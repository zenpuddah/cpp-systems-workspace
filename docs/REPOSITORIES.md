# Repository boundaries

| Repository | Visibility | Contents |
| --- | --- | --- |
| `cpp-systems-workspace` | Public | Technical specifications, OpenCode launch instructions, implementation progress |
| `cpp-systems-tools` | Public product candidate | Two completed tools, builds, tests, public diagrams/results and limitations |
| `cpp-systems-workbook` | Private | Pinned reference, untouched starters, private author material, learner attempts and companion |

Use independent sibling Git roots, not nested repositories or an outer repository tracking all three. Inspect existing directories and remotes first; reuse matching repositories without overwriting unrelated work.

Private preparation documents and their source history are not part of this public workspace. Publish only an explicit technical allowlist, with no personal study history, Library links, reference answers or learner snapshots.

Create requested target repositories through available authenticated hosting capabilities and verify actual visibility/URLs. If creation or credentials are unavailable, finish the local deliverables and report the remaining hosting step. Do not claim remote existence or change unrelated repository visibility.

Import a pinned allowlisted public reference into independent private workbook history. Keep author assessment code outside learner source capture and history ancestry, while recording assessment hashes/versions separately. The `learning/attempts` history has no automatic upstream or push. Never publish private context as a side effect of public delivery.
